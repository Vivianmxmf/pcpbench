## Guard threshold grid

leaderboard.md prints set/K to two decimal places and marginal to three decimal places, and the guard grid below recomputes each row's demotion from those displayed values at two and three decimals rather than from the unrounded values a row was actually computed from. The paper's own headline demotion, used for the default counts above and for the regime threshold grid, carries no such risk: it is read here straight from the table's own divider line, computed once from the unrounded values when leaderboard.md was generated. A row whose displayed set/K or marginal lands exactly on one of a guard cell's thresholds could have an unrounded value on either side of that threshold, so that cell's demoted count cannot be settled from the displayed table alone. Each guard row below therefore states the demoted count at displayed precision, the minimum it could take if every such row fell on the other side of its threshold instead, the maximum, which equals the displayed count because the table's own convention counts a tie as meeting the threshold, and how many rows were on a threshold for that cell. The exact grid, computed from every row's own unrounded marginal, mean set size, and number of classes, is produced with --outputs-dir where every headline row has its unrounded file.

The one exception is the guard cell whose three thresholds equal the defaults: leaderboard.md's own divider was computed with exactly those thresholds, so every row's demoted status there is already settled by the file's divider rather than merely bounded, and that cell's demoted minimum equals its demoted maximum even though some of its rows sit exactly on a threshold at displayed precision. The counts of that cell are the divider's. The displayed values alone would demote 1 more row there (ntu60_xsub/acp), which displays a value exactly on a threshold while the unrounded value the divider used falls short of it. The displayed table cannot confirm that; the grid computed with --outputs-dir does.
